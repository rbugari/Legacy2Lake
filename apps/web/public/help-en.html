Product help

Legacy2Lake is designed to help teams understand, prioritize, generate, review, and deliver complex modernization work. It is not just a “generate code” tool.

Core idea: the platform creates a better technical baseline and better evidence. It supports judgment; it does not replace it.

What It Is And Why It Exists

The product exists to reduce uncertainty in migrations where teams face legacy code, partial documentation, hidden dependencies, and expensive manual analysis.

  • it helps teams understand what is really in a repo or package
  • it helps classify what matters and what does not
  • it generates a useful baseline for review
  • it leaves behind evidence and delivery artifacts

Workflow

The workspace is stage-based. Each stage now has an overview landing page. That overview is the stage home: it tells you where you are, what to do next, and where to go for deeper work.

StagePurposeMain question
Discoveryunderstand the inputWhat did we ingest and how interpretable is it?
Triageclassify and prioritizeWhat is worth migrating and how should it be treated?
Draftinggenerate a first working baselineCan we produce a useful initial target?
Refinementimprove and validateCan we make that baseline stronger?
Governanceaudit and documentWhat evidence and findings does the solution leave behind?
Handoverpackage and deliverWhat is the final deliverable?
Current navigation model: the workspace no longer carries arbitrary subsections across stages. It remembers the last useful place within the same stage, but a new stage opens at a coherent entry point.

How To Use The Views

Overview

Overview is the recommended entry point for every stage. If you are unsure where to start, start there.

Logs

Use logs when a stage is running, taking too long, or producing something unclear.

Grid, Graph, Files, Comparison

These are working views. They help review decisions, inspect dependencies, and validate outputs before moving forward.

Important: actions such as Run Pipeline or Run Refinement are transient. They should not become your persistent landing state.

How To Get Better Value

  • do not run Drafting on top of weak Triage decisions
  • use Discovery and Triage to reduce noise before generation
  • add project context when business rules matter
  • use Governance to understand risk, not only to force approval
  • if an output looks wrong, go back to the right stage instead of patching everything at the end

System Limits

  • not every business rule can be inferred automatically
  • not every generated output is production-ready without review
  • direct mode aims for faithful baseline translation, not full redesign
  • PII, SCD2, or governance findings may reflect real project debt rather than platform failure
Practical rule: use the platform to think better and accelerate delivery, not to turn off team judgment.
