You are an expert Google Cloud Data Engineer. Generate Gold layer SQL that creates business-ready views optimized for Looker and BigQuery BI Engine.

### What is the Gold Layer in BigQuery?
The Gold layer is the **business presentation zone** where:
- Data is **aggregated** for analytics and Looker
- **Business calculations** and derived metrics
- **Denormalized** for query performance
- **Partitioned by date** for cost optimization
- **Materialized views** for performance
- **LookML-compatible** for Google Looker

### Your Mission:
Generate BigQuery SQL that:

1. **Reads from Silver dataset**
2. **Applies business logic** (calculations, aggregations)
3. **Creates Looker-ready tables/views**
4. **Handles DIMENSION vs FACT tables**
5. **Uses partitioning** for cost savings
6. **Supports BI Engine** caching
7. **Logs execution**

```sql
CREATE OR REPLACE TABLE `{project_id}.{dataset_gold}.{target_table}`

SELECT
    -- Primary/Foreign Keys
```

## ⚙️ Mandatory Requirements

### ✅ Table Types:

#### DIMENSION (Reference Data):
- Customer, Product, Date, Location
- Business-friendly names
- Status labels (CASE statements)
- Cluster by Primary Key

#### FACT (Transactional Data):
- Sales, Orders, Events
- Foreign keys to dimensions
- Computed measures (totals, averages)
- Cluster by DateKey (most common filter)

### ✅ Business Logic:
- Rename columns to business terms
- Add computed metrics: `quantity * unit_price`
- Create status labels: `CASE WHEN ... THEN`
- Handle division by zero: `SAFE_DIVIDE()`
- Filter historical data: `_ingestion_date >= DATE_SUB(...)`

### ✅ Optimization:
- **Partition by date:** Reduces scanned data and costs
- **Cluster by keys:** Co-locates related data
- **Materialized views:** Pre-computed for fast queries
- **BI Engine:** Enable caching for sub-second responses

```sql
-- Customer dimension for Looker

    _ingestion_timestamp AS last_updated

```

### Example 2: Fact (Sales)

```sql
-- Sales fact table for Looker
CREATE OR REPLACE TABLE `my-project.bi_gold.fact_sales`
PARTITION BY order_date
CLUSTER BY order_date, customer_key
AS
SELECT
    order_id AS order_key,
    customer_id AS customer_key,
    product_id AS product_key,
    order_date,
    
    -- Measures
    quantity,
    unit_price,
    quantity * unit_price AS gross_sales,
    quantity * unit_price * discount_pct AS discount,
    quantity * unit_price * (1 - discount_pct) AS net_sales,
    
    -- Profit
    (unit_price - cost) * quantity AS total_profit,
    SAFE_DIVIDE((unit_price - cost), unit_price) AS profit_margin,
    
    -- Flags
    IF(discount_pct > 0, TRUE, FALSE) AS is_discounted,
    
    _ingestion_timestamp AS processed_at
    
FROM `my-project.clean_silver.orders`
WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 365 DAY);

-- Materialized view for fast queries
CREATE MATERIALIZED VIEW `my-project.bi_gold.fact_sales_mv`
PARTITION BY order_date
CLUSTER BY order_date
AS
SELECT * FROM `my-project.bi_gold.fact_sales`;
```

## ❌ Common Mistakes

### 1. Division by Zero
```sql
-- ❌ WRONG: Can cause errors
net_sales / gross_sales AS margin

-- ✅ CORRECT: Use SAFE_DIVIDE
SAFE_DIVIDE(net_sales, gross_sales) AS margin
```

### 2. Not Filtering Old Data
```sql
-- ❌ WRONG: Scans entire table (expensive)
SELECT * FROM silver.orders

-- ✅ CORRECT: Filter by partition
SELECT * FROM silver.orders
WHERE order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 365 DAY)
```

### 3. Missing Partitioning
```sql
-- ❌ WRONG: No partitioning (high query costs)
CREATE OR REPLACE TABLE gold.fact_sales AS SELECT ...

-- ✅ CORRECT: Partition by date
CREATE OR REPLACE TABLE gold.fact_sales
PARTITION BY order_date
AS SELECT ...
```

## 💡 Best Practices

1. **Partition by date:** Mandatory for large fact tables
2. **Cluster by filters:** Keys frequently used in WHERE clauses
3. **Materialized views:** Pre-compute slow aggregations
4. **SAFE functions:** SAFE_DIVIDE, SAFE_CAST for error handling
5. **Filter old data:** Reduce scanned bytes and costs
6. **Business-friendly names:** Match Looker field names
7. **BI Engine:** Enable for sub-second dashboard responses

### Looker Integration:
- Use consistent naming (snake_case or camelCase)
- Create LookML views from Gold tables
- Define primary_key in LookML
- Use materialized views for explore performance
